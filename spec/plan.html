Phase 3

TMS complete example

Build a full Truck Management System using only YAML page configs and the core lib — no hand-coded UI logic per page. The goal is not just working pages: it is to discover every place the framework falls short, every repeated structure that deserves a shorthand, and every JS expression that could be a YAML property. All of that feeds back into the core lib.

Pattern-extraction rule When the same structure appears in two modules, write a YAML shorthand for it. When it appears in three, it becomes a first-class framework concept — a new component, prop, or layout type.

Design

Component meta model

Every component is driven by a ComponentDef config object — the declarative description of what to render and how to behave. The runtime reads this object and constructs the component tree. Inspired by the production core2 library's Component model.

// The full shape of a ComponentDef
{
  // Identity
  type:        string,   // 'GridView' | 'TextInput' | 'BadgeCell' | ...
  id:          string,   // unique within the page
  field:       string,   // data row key this component reads/writes

  // Display
  label:       string,
  align:       'left' | 'right' | 'center',
  column:      number,   // grid column span (1–12)
  row:         number,   // grid row position

  // Declarative expressions — evaluated via new Function(expr) with { user, row, state }
  show_if:     string,   // hide component when falsy  e.g. "user.hasRole('admin')"
  disabled_if: string,   // disable input when truthy  e.g. "state.saving"
  default:     string,   // initial value expression   e.g. "'Active'"
  compute:     string,   // derive cell value per row  e.g. "row.done / row.total"
  validation:  string,   // returns ValidationRule[]   e.g. "['required', 'minLength:3']"

  // Lifecycle events — map event name → handler name on the page/form
  events: {
    on_dom_ready:   string,   // fired after mount
    on_user_input:  string,   // fired on any field change
    on_before_save: string,   // fired before FormPanel.submit()
    on_after_save:  string,   // fired after successful submit
    on_disposed:    string,   // fired on component unmount
  },

  // Permissions — resolved from SecurityContext at render time
  can_read:    boolean,
  can_write:   boolean,
  can_delete:  boolean,

  // Data
  source:        string,   // datasource id for selects, lists, grids
  query:         string,   // override SQL query
  pre_query:     string,   // runs before main query (e.g. to seed params)
  is_realtime:   boolean,  // re-fetches on a polling interval
  group_by:      string,   // field name to group rows by
  group_format:  string,   // display template for group headers

  // Linked selects
  cascade_field:  string,  // sibling field that drives this select's options
  populate_field: string,  // field to auto-fill when this select changes

  // Actions (for ActionCell, Button, GridView toolbar)
  actions: ActionDef[],

  // Nested components (for FormPanel, TabPanel, SplitPanel)
  components: ComponentDef[],
}

ActionDef

{
  id:          string,   // action name passed to submit() / _onAction
  label:       string,
  variant:     'primary' | 'secondary' | 'danger' | 'ghost',
  show_if:     string,   // expression — hide action when falsy
  disabled_if: string,   // expression — disable when truthy
  confirm:     string,   // show ConfirmDialog before firing; supports {row.field}
  navigate_to: string,   // page id to navigate to instead of submitting
  params:      object,   // extra params; values support {row.field} interpolation
}
Design

Backend communication

All data flows through two DTOs: SqlViewModel for reads and PatchVM for writes. A single Client singleton handles JWT auth and token refresh. This mirrors the proven pattern from the production core2 library.

SqlViewModel — query DTO

// Sent to the datasource adapter for all reads
{
  sourceId:   string,    // datasource id from page config
  action:     string,    // 'query' | 'count' | 'aggregate'
  params:     object,    // bound values (from FilterBar state, URL params, etc.)
  select:     string[],  // fields to return; omit for *
  where:      string,    // SQL WHERE fragment (parameterised)
  orderBy:    string,    // e.g. 'plate ASC, last_service DESC'
  groupBy:    string,    // e.g. 'branch_id'
  skip:       number,    // pagination offset
  top:        number,    // page size
  metaConn:   string,    // connection id for metadata queries
  dataConn:   string,    // connection id for data queries
}

PatchVM — write DTO

// Sent for create / update / delete
{
  table:   string,          // target table name
  changes: [
    { field: string, label: string, oldVal: any, value: any }
  ],
  action:  'create' | 'update' | 'delete',
  id:      string | number, // row id for update/delete
}

Client singleton

// lib/client.js — one instance shared by all datasource adapters
class Client {
  // Reads API base from <meta name="api">, then VITE_API_URL, then window.location.origin
  static resolveApiBase()

  // JWT-aware fetch — silently refreshes access token if expired before each call
  async submitAsync({ url, method, body, headers })

  // High-level operations
  async query(vm: SqlViewModel): Promise<DataResponse>
  async patch(vm: PatchVM):      Promise<{ id: string | number }>
  async patchMany(vms: PatchVM[]): Promise<void>   // batch upsert, 200/batch
  async deactivate(ids, table)
  async hardDelete(ids, table)
  async uploadFile(file, url)
}
DuckDB vs HTTP adapter In Phase 2, Client.query() routes to DuckDB WASM directly in the browser when protocol: duckdb. When protocol: http, it falls back to a normal fetch to the backend API. The datasource adapter resolves which transport to use at runtime — page configs do not change.
Phase 3 output

Patterns to extract into the framework

Each pattern is a hypothesis — building the TMS will confirm or refine it. When a pattern shows up in three or more places, it gets promoted to a first-class YAML property or component.

Master-detail navigation

layout

Every list page has a View action that navigates to a detail page passing a row ID. Should be fully declarable — no JS handler needed.

actions:
  - id: view
    label: View
    navigate_to: truck-detail
    params: { id: "{row.id}" }

Conditional visibility

access

Actions and fields visible only to certain roles. Expression evaluated against { user, row, state } via new Function — the same pattern core2 uses for showExp.

- id: deactivate
  label: Deactivate
  variant: danger
  show_if: "user.hasRole('admin')"
  confirm: "Deactivate {row.name}?"

Confirm dialog

interaction

Destructive actions need a confirmation step. A confirm string on any ActionDef auto-shows a ConfirmDialog before submit() fires. Message supports {row.field} interpolation.

- id: delete
  label: Delete
  variant: danger
  confirm: "Delete truck {row.plate}? This cannot be undone."

Cascading select

form

Branch → truck type → available trucks. Each select re-fetches its options when the named sibling changes. Core2 calls this cascadeField; we map it to depends_on.

- type: SelectInput
  field: branch_id
  label: Branch
- type: SearchEntry
  field: truck_id
  label: Truck
  source: available-trucks
  depends_on: branch_id

Computed / derived fields

data

Utilization %, rank, fuel efficiency — calculated from raw row data. Simple inline expressions replace a full datasource script. Core2 uses Utils.isFunction(exp); we use the same new Function approach.

- type: NumberCell
  field: utilization
  label: Utilization %
  format: percent
  compute: "row.active_days / row.total_days"

Export action

data

Reports need CSV / XLSX / PDF export. Should be a top-level GridView prop that renders ButtonExcel / ButtonPdf in the toolbar — no custom JS.

type: GridView
export:
  - format: xlsx
    label: Export Excel
  - format: pdf
    label: Print report

Summary row

data

Trip log and cost analysis need a totals row. Should aggregate NumberCell and CurrencyCell columns automatically when summary_row: true is set.

type: GridView
summary_row: true

Inline edit

grid

Settings / Branches needs in-place cell editing. An inline_edit: true column prop toggles a TextCell into a TextInput on click; Blur / Enter commits via submit('cell.update', …).

- type: TextCell
  field: name
  label: Branch name
  inline_edit: true

Permission flags

access

Every component can carry can_read, can_write, can_delete booleans resolved at render time from the current user's SecurityContext. Actions are hidden automatically when the required permission is false.

type: GridView
can_write: true
can_delete: false  # resolved per-user at runtime

Lifecycle events

behaviour

Pages need hooks into component lifecycle — e.g. pre-populate a form field after mount, validate before save, refresh a grid after a form submits. Core2 models these as typed Action observables. We expose them as named event handlers in the page config.

components:
  - type: FormPanel
    id: truck-form
    events:
      on_dom_ready:   initForm      # called after mount
      on_before_save: validatePlate # return false to cancel
      on_after_save:  refreshGrid   # refresh fleet-grid after save
