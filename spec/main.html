Why this exists

Vision

ERP systems are complex: dozens of CRUD views, real-time dashboards, approval workflows, report builders, and integrations with external services. Most teams spend more time on plumbing than on business logic.

The framework eliminates that plumbing. A single YAML file declares the UI layout, data sources, queries, and communication protocol. The framework reads the YAML and assembles a fully working page — backend data pipeline included — using a library of built-in components that snap together like LEGO.

Under the hood, rendering is powered by html.js (the fastest DOM-rendering library available), wrapped in an OOP component model that gives developers inheritance, encapsulated state, and explicit draw() / redraw() lifecycle hooks.

Foundation

Core pillars

Five capabilities that make the framework work as a unified system.

Core

YAML-Driven Assembly

Pages, components, data sources, queries, and protocols are declared in human-readable YAML. An agent or developer can author, review, and diff a page definition without touching application code.

Frontend

OOP Rendering & Tree

Components live in a tree with pure JSON state. Any node traverses to parent, children, or root for state access. Named actions are submitted to the backend via submit(action, params).

Backend

Embedded SQL & Repository

SQL queries live inside the YAML definition. The repository pattern abstracts the database engine — switch from PostgreSQL to DuckDB by changing one line. Built-in CRUD operations cover 80% of ERP data needs.

Backend

Custom Scripting

Embed logic in any language — JavaScript, TypeScript, Python, Lua, or Shell — directly in the YAML. Declare language, write the script inline or reference an external file.

Infra

Multi-Protocol Comms

Each data source in the YAML specifies its transport: HTTP for request/response, WebSocket for bidirectional streaming, SSE for server push. The framework negotiates the protocol so components just consume data.

UI layer

Frontend rendering model

Every component is a class in a tree, with pure JSON state and full traversal. Under the hood, html.js handles the DOM for raw speed.

Base component class

All components inherit from BaseComponent. The class owns its state as pure JSON, mounts into a DOM target, and exposes lifecycle methods plus full tree traversal:

abstract class BaseComponent<S = any> {
  state: S;                          // pure JSON — serializable, inspectable, diffable
  readonly parent: BaseComponent | null;
  readonly children: BaseComponent[];
  readonly root: BaseComponent;      // always the top-level page component
  readonly id: string;

  abstract draw(container: HTMLElement): void;
  redraw(): void { ... }             // can differ from draw — patch only what changed
  setState(partial: Partial<S>, redraw?: boolean): void { ... }  // redraw defaults to true

  /** Find a component anywhere in the tree by id */
  find(id: string): BaseComponent | null;

  /** Submit a named action to the backend */
  submit(action: string, params?: Record<string, any>): Promise<any>;
}

Why redraw is separate from draw, and why setState can skip it. The framework does not blindly trust the rendering engine to diff efficiently everywhere. draw() builds the full DOM subtree from scratch — correct but expensive. redraw() can be overridden to patch only what changed, avoiding a full teardown of the component tree. And setState(partial, false) lets you batch multiple state changes across the tree before triggering a single coordinated redraw — giving developers explicit control over data flow instead of relying on automatic cascades that may over-render.

Component tree & state traversal

Every component lives in a tree. Any node can walk up to its parent, down to its children, or straight to the root. State is always pure JSON — no class instances, no hidden getters, no observables:

class LineItemEditor extends BaseComponent<{ items: LineItem[] }> {
  draw(el: HTMLElement) {
    // read parent's state (the PO header)
    const poHeader = this.parent.state;         // { vendor, ship_to, payment_terms }

    // read root page state (global context)
    const globalCtx = this.root.state;          // { user, permissions, pageTitle }

    // read sibling data via parent's children
    const summary = this.parent.children
      .find(c => c.id === "po-summary")?.state; // { total, itemCount }

    // collect all children state
    const allRows = this.children.map(c => c.state); // [{ qty, price }, ...]
  }
}

//   PageRoot (root.state = global context)

//   │   │   └── Row2 (child.state = { qty: 3, price: 250 })

Frontend actions

Components submit named actions to the backend using submit(action, params). The action name maps to a handler declared in the YAML — either a SQL mutation, a custom script, or an API call:

class ApproveButton extends BaseComponent<{ loading: boolean }> {
  draw(el: HTMLElement) {
    html(el)
      .button("Approve PO")
        .cls("btn-primary")
        .on("click", async () => {
          this.setState({ loading: true }, false);   // update state, skip redraw

          const po = this.parent.state;
          const result = await this.submit("approve_po", {
            po_id: po.id,
            approved_by: this.root.state.user.id,
            line_items: this.parent.children
              .find(c => c.id === "line-items")
              ?.children.map(c => c.state)
          });

          this.parent.setState({ status: result.status }); // redraws parent (default)
        })
      .end();
  }
}

React interop

For teams that need the React ecosystem (rich date pickers, charting libraries, etc.), a ReactBridge adapter lets React components live inside the rendering tree. The framework owns the lifecycle; React renders within a managed mount point.

LEGO assembly from YAML

A page can be assembled without writing any backend code. The YAML declares which built-in components to use and how to arrange them:

Server-first data & component-based rendering

Traditional grid implementations split work awkwardly: the backend returns raw IDs, the frontend resolves them via reference lookups, and column definitions sit in a configuration limbo — neither true components nor pure data. This creates coupling, duplicated logic, and prevents columns from participating in the component tree.

The framework takes a different approach: the server sends a flat 1D array with all data fully resolved — every JOIN, lookup, and transformation happens server-side in a single query or function. On the frontend, what were formerly "columns" are now components — real BaseComponent instances that live in the virtual tree, have their own state, can traverse to parent/children/root, and can submit actions to the server. All event handling is centralized in a single class at the page level, inherited from BaseComponent.

This pattern is not GridView-specific. It applies uniformly to ListView, TreeView, PDF reports, or any view that requires complex query and rendering.

Server side: all burden here

The backend returns a flat array of fully resolved rows. No reference sets, no client-side lookups. One query (or function) does all the work:

# Backend datasource — flat, fully resolved data
datasources:
  - id: purchase-orders
    db: postgres
    protocol: http
    roles: [admin, purchasing]
    permission: "po.read"
    query: |
      SELECT
        po.id,
        po.po_number,
        v.name AS vendor_name,
        v.code AS vendor_code,
        s.label AS status_label,
        s.color AS status_color,
        s.icon AS status_icon,
        b.name AS branch_name,
        po.total,
        po.created_at
      FROM purchase_orders po
      JOIN vendors v ON v.id = po.vendor_id
      JOIN po_status_codes s ON s.code = po.status
      JOIN branches b ON b.id = po.branch_id
      WHERE po.branch_id IN (:allowed_branches)
      ORDER BY po.created_at DESC

When static SQL isn't enough — dynamic filters, multi-tenant routing, or data assembled from multiple sources — use a function. The function returns a single flat array:

# Programmatic: function returns flat 1D array
datasources:
  - id: purchase-orders
    roles: [admin, purchasing]
    permission: "po.read"
    language: javascript
    script: |
      const orders = await ctx.db.query(`
        SELECT
          po.id, po.po_number,
          v.name AS vendor_name, v.code AS vendor_code,
          s.label AS status_label, s.color AS status_color,
          b.name AS branch_name,
          po.total, po.created_at
        FROM purchase_orders po
        JOIN vendors v ON v.id = po.vendor_id
        JOIN po_status_codes s ON s.code = po.status
        JOIN branches b ON b.id = po.branch_id
        WHERE po.branch_id IN (:branches)
        ORDER BY po.created_at DESC
      `, { branches: ctx.user.branches });

      // apply business logic the database can't express
      return orders.map(o => ({
        ...o,
        overdue: o.status_label === 'Pending'
          && daysSince(o.created_at) > 30,
        editable: ctx.user.roles.includes('purchasing')
      }));

The response shape is intentionally simple — no reference maps, no multi-result sets:

interface DataResponse {
  data: Record<string, any>[];   // flat 1D array — every field already resolved
  meta: { total: number; page: number; pageSize: number; };
}

In the frontend YAML, what were formerly called "columns" are now components. Each one is a real BaseComponent instance that participates in the virtual tree — with state, traversal, and actions — just like any other component in the framework:

Because these are real components, each cell instance lives in the tree and has full access to traversal, state, and actions:

// Component tree — every cell is a real BaseComponent
//
//   PageRoot (root.state = global context)
//   ├── POGridEvents  (event handler — declared at page level)
//   ├── GridView (po-grid)
//   │   ├── Row0
//   │   │   ├── TextCell (po-number)     ← traversable, has state
//   │   │   ├── TextCell (vendor)        ← can read grid.state, root.state
//   │   │   ├── CurrencyCell (amount)    ← can submit actions to server
//   │   │   ├── BadgeCell (status)       ← redraws independently
//   │   │   ├── TextCell (branch)        ← finds siblings via parent.children
//   │   │   └── DateCell (created)       ← participates in draw/redraw cycle
//   │   ├── Row1
//   │   │   └── ...
//   │   └── ...
//   └── SummaryCard (totals)

class BadgeCell extends BaseComponent<{ value: string; color: string; icon: string }> {
  draw(el: HTMLElement) {
    html(el)
      .span(this.state.value)
        .cls("badge")
        .style("background", this.state.color)
        .attr("data-icon", this.state.icon)
      .end();
  }

  // Real component: traverse the tree
  getRowTotal(): number {
    const amountCell = this.parent.children.find(c => c.id === "amount");
    return amountCell?.state.value ?? 0;
  }

  // Real component: submit actions
  async markApproved() {
    const rowData = this.parent.state;
    await this.submit("approve_po", { po_id: rowData.id });
    this.setState({ value: "Approved", color: "#16a34a" });
  }
}

class GridView extends BaseComponent<GridViewState> {
  private componentDefs: ComponentDef[];

  onDataLoad(response: DataResponse) {
    // flat data — no reference resolution, no lookup maps
    this.setState({ rows: response.data, meta: response.meta });
  }

  draw(el: HTMLElement) {
    const grid = html(el).div().cls("gridview");

    // header from component labels
    const header = grid.div().cls("grid-header");
    for (const def of this.componentDefs) {
      header.div(def.label).cls("grid-th").style("width", def.width).end();
    }
    header.end();

    // each row spawns real child components
    const body = grid.div().cls("grid-body");
    for (const row of this.state.rows) {
      const rowComp = this.createChild(RowComponent, { data: row });
      for (const def of this.componentDefs) {
        // each cell is a BaseComponent — added to the tree, fully traversable
        rowComp.createChild(def.type, {
          value: row[def.field],
          ...this.extractProps(def, row)
        });
      }
      rowComp.draw(body);
    }
    body.end();
    grid.end();
  }
}

Page-level event handler

All event listeners for a data view are handled by a single class declared at the top level of the page. This class inherits from BaseComponent, giving it full tree access. The focus is on data flow — server → components → user interaction → actions → server. UI interaction is not limited; it is channeled through a predictable, debuggable path:

class POGridEvents extends BaseComponent<{ selectedIds: string[] }> {
  // Declared at page level — one class handles all grid interactions

  onCellClick(cell: BaseComponent, row: Record<string, any>) {
    // cell is the actual component in the tree — full traversal available
    if (cell.id === "status") {
      this.showStatusDropdown(cell, row);
    }
  }

  onRowSelect(rows: Record<string, any>[]) {
    this.setState({ selectedIds: rows.map(r => r.id) });
    // update sibling components via tree traversal
    const summary = this.root.find("totals");
    summary?.setState({
      selectedTotal: rows.reduce((s, r) => s + r.total, 0),
      selectedCount: rows.length
    });
  }

  async onBulkAction(action: string) {
    const result = await this.submit(action, {
      po_ids: this.state.selectedIds,
      user_id: this.root.state.user.id
    });
    // server returns updated flat data — just refresh
    const grid = this.root.find("po-grid");
    grid?.setState({ rows: result.data });
  }

  private showStatusDropdown(cell: BaseComponent, row: Record<string, any>) {
    // UI enhancement — not limited, but channeled through data flow
    const dropdown = this.root.find("status-dropdown");
    dropdown?.setState({ visible: true, anchorTo: cell, currentRow: row });
  }
}
# YAML declaration — event handler at page level
page:
  title: Purchase Orders

  # Event handler: single class, declared at top level
  events:
    class: POGridEvents
    handles:
      - target: po-grid
        on: [cellClick, rowSelect, bulkAction]
      - target: po-detail
        on: [fieldChange, save]

Generalizable pattern

This is not a GridView-specific design. The same three-part pattern — server-first flat data, component-based rendering, page-level event handler — applies to any view that requires complex query and rendering:

View

GridView

Tabular data. Components are cells — TextCell, BadgeCell, CurrencyCell. Each cell is traversable and actionable.

View

ListView

Vertical list with rich items. Components are list item parts — avatar, title, subtitle, actions. Same flat data, same event handler.

View

TreeView

Hierarchical data (org charts, BOM). Server sends flat array with parent_id — components build the visual hierarchy client-side.

View

PDF Report

Server sends fully resolved data. Components define report sections — header, table, chart, summary. Same data flow, rendered to PDF instead of DOM.

# ListView — same pattern, different view type
components:
  - type: ListView
    id: vendor-list
    source: vendors-flat        # server sends flat 1D array
    components:
      - type: AvatarItem
        id: vendor-avatar
        field: logo_url
      - type: TitleItem
        id: vendor-name
        field: name
        secondary: region
      - type: StatusItem
        id: vendor-status
        field: status_label
        color: status_color

# TreeView — flat data with parent_id, rendered as hierarchy
components:
  - type: TreeView
    id: category-tree
    source: categories-flat     # flat array, parent_id builds the tree
    parentField: parent_id
    components:
      - type: TreeLabel
        id: cat-name
        field: name
        icon: icon
      - type: CountBadge
        id: cat-count
        field: product_count

Why this matters for ERP at scale:

  • Server owns data complexity. All JOINs, lookups, and transformations happen in one place — a single query or function. The frontend never resolves references or builds lookup maps. It receives display-ready data.
  • Components are real components. Every cell, list item, or tree node is a BaseComponent in the virtual tree — with state, traversal, and actions. No special-case "column definition" rendering.
  • Data flow is explicit. Server → flat data → components → user events → page-level handler → actions → server. Every step is traceable. No hidden cascades, no implicit reference resolution.
  • Event handling is centralized. One class per page handles all interactions for all data views. Debuggable, testable, easy to reason about — while still allowing rich UI through the component tree.
  • One pattern, many views. GridView, ListView, TreeView, PDF — all use the same three-part pattern. Learn it once, apply it everywhere.
Data layer

Backend data pipeline

The repository pattern with permission-gated queries, embedded SQL in YAML, and support for four database engines.

Repository pattern

Each repository implements a common interface. Switching databases is a one-line config change. Every operation — including raw query() — is gated by the role and permission declared in the YAML datasource definition:

interface IRepository<T> {
  findById(id: string): Promise<T | null>;
  findMany(filter: Filter<T>): Promise<T[]>;
  create(entity: T): Promise<T>;
  update(id: string, partial: Partial<T>): Promise<T>;
  delete(id: string): Promise<void>;
  query(sql: string, params?: any[]): Promise<T[]>;
}

// Before executing query(), the framework enforces:
//   1. roles  — user must hold at least one declared role
//   2. permission — user must have the specific permission
// Both are declared per-datasource in YAML (see below)

YAML role & permission gates

Each datasource declares who can access it. The framework rejects the request before the query runs if the user does not satisfy the gate:

# example: role-gated datasource
datasources:
  - id: user-profiles
    db: postgres
    protocol: http
    roles: [admin]                     # only admins can execute this query
    permission: "profile access"       # must also hold this permission
    query: |
      SELECT * FROM user_profile
      WHERE branch_id IN (:allowed_branches)
    component: EditableGridView        # renders as an editable grid

  - id: order-summary
    db: postgres
    protocol: http
    roles: [admin, manager]
    permission: "orders.read"
    query: |
      SELECT id, customer, total, status FROM orders
      ORDER BY created_at DESC
    component: data-table

Embedded SQL in YAML

Queries are declared inline. The framework parameterizes inputs to prevent injection, applies row-level permission filters from the auth layer, and returns typed results:

# data-source definition in YAML
datasources:
  - id: recent-orders
    db: postgres            # swap to: duckdb | sqlserver | sqlite
    protocol: http          # or: websocket | sse
    roles: [admin, sales]
    permission: "orders.read"
    query: |
      SELECT o.id, c.name AS customer, o.total, o.status
      FROM orders o
      JOIN customers c ON c.id = o.customer_id
      WHERE o.created_at > :since
        AND o.branch_id IN (:allowed_branches)   -- injected by auth
      ORDER BY o.created_at DESC
    params:
      since: { type: date, default: "-30d" }
    cache: { ttl: 60s }

CRUD operations

Datasources are not read-only. Each datasource can declare create, update, and delete operations alongside the query. Use default flags for standard table mutations, or custom functions when business logic is involved.

Default CRUD flags

Set crud: true to auto-generate all three mutations from the table schema. Or pick specific operations with an array. The framework generates parameterized INSERT, UPDATE, and DELETE statements — no SQL to write:

datasources:
  # Full CRUD — framework generates all mutations
  - id: vendors
    db: postgres
    table: vendors
    roles: [admin, purchasing]
    permission: "vendors.manage"
    crud: true                    # shorthand: create + update + delete
    query: |
      SELECT id, name, code, region, status, created_at
      FROM vendors
      ORDER BY name

  # Selective — only allow update and delete, no create
  - id: po-lines
    db: postgres
    table: po_line_items
    roles: [admin, purchasing]
    permission: "po.edit"
    crud: [update, delete]        # array: pick specific operations
    query: |
      SELECT li.id, li.item_id, p.name AS item_name,
             li.qty, li.unit_price, (li.qty * li.unit_price) AS total
      FROM po_line_items li
      JOIN products p ON p.id = li.item_id
      WHERE li.po_id = :po_id
    params:
      po_id: { type: uuid, bind: po-detail.id }

When crud: true, the framework reads the table schema and generates:

OperationGenerated SQLFrontend call
CreateINSERT INTO {table} (...) VALUES (...) RETURNING *submit("vendors.create", data)
UpdateUPDATE {table} SET ... WHERE id = :id RETURNING *submit("vendors.update", { id, ...data })
DeleteDELETE FROM {table} WHERE id = :idsubmit("vendors.delete", { id })

Every generated mutation respects the same roles and permission gate declared on the datasource. Row-level filters (:allowed_branches) are injected into the WHERE clause automatically.

Custom CRUD functions

When default flags aren't enough — validation, multi-table writes, audit logging, or side effects — declare a custom function for any operation. Mix and match: use defaults for simple operations and functions for complex ones:

datasources:
  - id: purchase-orders
    db: postgres
    table: purchase_orders
    roles: [admin, purchasing]
    permission: "po.manage"
    query: |
      SELECT po.id, po.po_number, v.name AS vendor_name,
             s.label AS status_label, po.total, po.created_at
      FROM purchase_orders po
      JOIN vendors v ON v.id = po.vendor_id
      JOIN po_status_codes s ON s.code = po.status
      WHERE po.branch_id IN (:allowed_branches)
      ORDER BY po.created_at DESC

    # Default delete — no custom logic needed
    crud: [delete]

    # Custom create — validation + multi-table + auto-numbering
    create:
      language: javascript
      permission: "po.create"
      script: |
        const { vendor_id, ship_to, payment_terms, line_items } = ctx.params;
        if (!line_items?.length) {
          throw new ValidationError("PO must have at least one line item");
        }
        const po = await ctx.db.create("purchase_orders", {
          po_number: await ctx.db.nextSequence("po_number_seq"),
          vendor_id, ship_to, payment_terms,
          status: "draft",
          total: line_items.reduce((s, li) => s + li.qty * li.unit_price, 0),
          created_by: ctx.user.id,
          branch_id: ctx.user.branch_id
        });
        for (const li of line_items) {
          await ctx.db.create("po_line_items", { po_id: po.id, ...li });
        }
        return po;

    # Custom update — approval logic + notifications
    update:
      language: javascript
      permission: "po.edit"
      script: |
        const { id, ...changes } = ctx.params;
        const current = await ctx.db.findById("purchase_orders", id);
        if (current.status === "approved" && !ctx.user.roles.includes("director")) {
          throw new ValidationError("Cannot edit an approved PO");
        }
        if (changes.line_items) {
          changes.total = changes.line_items
            .reduce((s, li) => s + li.qty * li.unit_price, 0);
        }
        const updated = await ctx.db.update("purchase_orders", id, changes);
        if (changes.status === "approved") {
          await ctx.submit("send_notification", {
            to: "purchasing",
            message: `PO ${current.po_number} approved`
          });
        }
        return updated;

CRUD in the component tree

Components call CRUD operations through the same submit() method used for any action. The naming convention is {datasource_id}.{operation}:

class VendorRow extends BaseComponent<{ id: string; name: string; editing: boolean }> {
  async save() {
    // uses the default update — no custom function needed
    const updated = await this.submit("vendors.update", {
      id: this.state.id,
      name: this.state.name
    });
    this.setState({ ...updated, editing: false });
  }

  async remove() {
    await this.submit("vendors.delete", { id: this.state.id });
    // parent grid handles row removal via event handler
  }
}

class AddVendorForm extends BaseComponent<{ name: string; code: string }> {
  async create() {
    const vendor = await this.submit("vendors.create", this.state);
    // event handler refreshes the grid with new data
    this.setState({ name: "", code: "" });
  }
}
Multi-language

Custom scripting engine

SQL covers most data needs, but ERP workflows often require custom logic — validation rules, complex calculations, data transformations, or calls to external APIs. Declare language and write code inline or reference an external file.

The framework spawns a sandboxed runtime for the declared language, passes the execution context (user, params, previous datasource results), and collects the return value as the datasource output. Role and permission gates apply exactly the same way as SQL datasources.

TypeScriptV8 isolate + ts-stripSame as JS with type safety

Inline script in YAML

# datasource with inline JavaScript
datasources:
  - id: enriched-orders
    language: javascript
    roles: [admin, sales]
    permission: "orders.read"
    script: |
      const orders = await ctx.datasource("recent-orders");
      const enriched = orders.map(order => ({
        ...order,
        tax: order.total * 0.08,
        grand_total: order.total * 1.08,
        priority: order.total > 10000 ? "high" : "normal"
      }));
      return enriched;
    component: data-table

  # datasource with inline Python
  - id: sales-forecast
    language: python
    roles: [admin, analyst]
    permission: "reports.forecast"
    script: |
      import pandas as pd
      orders = ctx.datasource("recent-orders")
      df = pd.DataFrame(orders)
      df['date'] = pd.to_datetime(df['created_at'])
      monthly = df.groupby(df['date'].dt.to_period('M'))['total'].sum()
      forecast = monthly.rolling(3).mean().iloc[-1]
      return { "monthly": monthly.to_dict(), "next_month": forecast }
    component: summary-card

Execution context

Every script receives a ctx object with access to the current user, parameters, other datasource results, and utility functions:

interface ScriptContext {
  user: User;                                       // current authenticated user
  params: Record<string, any>;                      // resolved YAML params
  datasource(id: string): Promise<any>;             // fetch another datasource
  db: IRepository;                                  // direct DB access (permission-gated)
  http: { get, post, put, delete };                 // sandboxed HTTP client
  log: Logger;                                      // structured logging
  env: Record<string, string>;                      // allowed environment variables
}
Styling

CSS system

The framework uses Tailwind CSS as the default styling system. Components apply utility classes directly in their draw() methods — no separate stylesheet files, no CSS-in-JS runtime, no naming conventions to learn.

Tailwind's utility-first approach aligns with the framework's philosophy: the component class is the source of truth for both structure and appearance. A developer reading draw() sees exactly what the component looks like without jumping to a stylesheet.

Utility classes in components

Components apply Tailwind classes via html.js chaining. The .cls() method accepts space-separated utilities:

class BadgeCell extends BaseComponent<{ value: string; color: string }> {
  draw(el: HTMLElement) {
    html(el)
      .span(this.state.value)
        .cls("inline-flex items-center px-2.5 py-0.5 rounded-full text-xs font-medium")
        .cls(this.state.color)    // dynamic: "bg-green-100 text-green-800"
      .end();
  }
}

class GridView extends BaseComponent<GridViewState> {
  draw(el: HTMLElement) {
    const grid = html(el).div()
      .cls("overflow-hidden rounded-lg border border-gray-200 shadow-sm");

    const header = grid.div().cls("grid-header bg-gray-50 border-b border-gray-200");
    for (const def of this.componentDefs) {
      header.div(def.label)
        .cls("px-4 py-3 text-left text-xs font-medium text-gray-500 uppercase tracking-wider")
      .end();
    }
    header.end();

    const body = grid.div().cls("divide-y divide-gray-200 bg-white");
    for (const row of this.state.rows) {
      const rowComp = this.createChild(RowComponent, { data: row });
      rowComp.draw(body);
    }
    body.end();
    grid.end();
  }
}

Escape hatch

When Tailwind utilities aren't enough — complex animations, third-party widget styling, or pixel-perfect print layouts — components can use .style() for inline CSS or inject a scoped <style> block. The framework does not prevent raw CSS; it just defaults to Tailwind for consistency across teams.

class SparklineCell extends BaseComponent<{ points: number[] }> {
  draw(el: HTMLElement) {
    const svg = html(el).svg()
      .cls("w-20 h-6")
      .style("shape-rendering", "geometricPrecision")   // inline escape hatch
      .attr("viewBox", `0 0 80 24`);
    // ... draw polyline from this.state.points
    svg.end();
  }
}
Security

Authentication & authorization

The framework does not implement authentication itself. It defines a pluggable interface that the host application implements — keeping the library infrastructure-agnostic.

interface IAuthProvider {
  getCurrentUser(): Promise<User | null>;
  hasPermission(user: User, action: string, resource: string): boolean;
  getSecurityContext(user: User): SecurityContext;
}

// The host app plugs in its own implementation
framework.configure({
  auth: new MyOAuth2AuthProvider({ ... })
});

Every data source query and component render checks permissions through this interface. Row-level security context values (like :allowed_branches) are injected into SQL parameters automatically.

datasources:
  # Query: server does all JOINs, returns flat 1D array
  - id: recent-pos
    db: postgres
    protocol: http
    roles: [admin, purchasing]
    permission: "po.read"
    query: |
      SELECT po.id, po.po_number,
             v.name AS vendor_name, v.code AS vendor_code,
             s.label AS status_label, s.color AS status_color,
             po.total, po.created_at
      FROM purchase_orders po
      JOIN vendors v ON v.id = po.vendor_id
      JOIN po_status_codes s ON s.code = po.status
      WHERE po.branch_id IN (:allowed_branches)
      ORDER BY po.created_at DESC

  # CRUD: default flags for simple operations
  - id: po-by-id
    db: postgres
    protocol: http
    table: purchase_orders
    roles: [admin, purchasing]
    permission: "po.manage"
    crud: [update, delete]           # default update + delete

      SELECT po.*, v.name AS vendor_name, v.code AS vendor_code
      FROM purchase_orders po
      JOIN vendors v ON v.id = po.vendor_id
      WHERE po.id = :id

      id: { type: uuid, from: route }

    # Custom create — validation + multi-table insert
    create:
      language: javascript
      permission: "po.create"
      script: |
        const { vendor_id, ship_to, payment_terms, line_items } = ctx.params;
        if (!line_items?.length) {
          throw new ValidationError("PO requires at least one line item");
        }
        const po = await ctx.db.create("purchase_orders", {
          po_number: await ctx.db.nextSequence("po_number_seq"),
          vendor_id, ship_to, payment_terms,
          status: "draft",
          total: line_items.reduce((s, li) => s + li.qty * li.unit_price, 0),
          created_by: ctx.user.id,
          branch_id: ctx.user.branch_id
        });
        for (const li of line_items) {
          await ctx.db.create("po_line_items", { po_id: po.id, ...li });
        }
        return po;

  # CRUD: full default on line items
  - id: po-lines
    db: postgres
    protocol: websocket
    table: po_line_items
    roles: [admin, purchasing]
    permission: "po.edit"
    crud: true                       # all three: create, update, delete
    query: |
      SELECT li.id, li.item_id, p.name AS item_name,
             li.description, li.qty, li.unit_price,
             (li.qty * li.unit_price) AS total

      JOIN products p ON p.id = li.item_id

Philosophy

Design principles

  • Convention over configuration — sensible defaults, override only when needed
  • YAML is the source of truth — if it's not in the YAML, it doesn't exist on the page
  • One line to switch — database, protocol, or auth provider
  • No black boxes — every built-in component can be extended or replaced
  • Agent-friendly — YAML definitions are structured enough for AI agents to read, generate, and modify
  • Security by default — parameterized queries, row-level auth, permission checks on every render and data fetch
