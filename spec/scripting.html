Multi-language

Custom scripting engine

YAML is the first-class definition. Custom source code is a build input, not production server code: the build pipeline compiles it to WebAssembly, validates the module, and the server executes only the resulting WASM artifact through a capability-limited host interface.

YAML workflows are the first-class model

Business workflows are declared in YAML before custom code is considered. A workflow definition owns its states, transitions, permissions, guards, persistence, and audit behavior. The runtime validates the transition from the current persisted state and applies the resulting state change server-side.

# workflows/orders.yaml
workflow:
  id: orders
  entity: orders
  state:
    val: status
    text: status_text
    initial: Draft

  transitions:
    - id: submit_for_approval
      from: [Draft]
      to: Pending Approval
      permission: orders.write
      audit: Submit order for approval

    - id: approve
      from: [Pending Approval]
      to: Approved
      permission: orders.approve
      guard:
        all:
          - field: total_amount
            operator: greater_than
            value: 0
          - field: customer_id
            operator: present
      audit: Approve order

    - id: reject
      from: [Pending Approval]
      to: Draft
      permission: orders.approve
      audit: Return order to draft

    - id: cancel
      from: [Draft, Pending Approval, Approved]
      to: Cancelled
      permission: orders.write
      audit: Cancel order

  persistence:
    update: { val: status, text: status_text }
    audit_table: system_activity

The page references a workflow transition by ID; it does not reproduce the transition rules:

actions:
  - id: approve_order
    type: workflow
    workflow: orders
    transition: approve
    permission: orders.approve
    refresh: [orders]

Workflow execution contract

  • The server loads the workflow YAML and treats it as the authoritative transition graph.
  • The server reads the current state from the persisted record; the client cannot choose the source state.
  • The server checks permission, row scope, guard conditions, and transition validity before writing.
  • The server writes the target state and its display text as one mutation, then records the audit event.
  • JavaScript is an extension point for guards or effects that cannot be expressed declaratively; it is not the workflow definition.

WebAssembly security boundary

Production custom logic crosses the server boundary only as WebAssembly. A WASM module has no implicit access to the filesystem, process, network, environment, database connection, secrets, or host memory. Every operation must be exposed deliberately through a typed host capability declared by YAML.

script:
  id: calculate-order-totals
  source: ./scripts/calculate-order-totals.ts
  language: typescript
  compile:
    target: wasm32-wasi
    toolchain: configured-build-image
    optimize: release
  capabilities:
    - datasource.read: orders
    - datasource.read: order_lines
  limits:
    memory_mb: 64
    fuel: 1000000
    timeout_ms: 500
  output: json

Execution rules

  • The server never evaluates arbitrary JavaScript, TypeScript, Python, Lua, or Shell source in the request path.
  • Compilation happens in a controlled build environment; deployment ships the compiled module, checksum, source metadata, and declared capabilities.
  • The WASM runtime denies undeclared imports and enforces memory, fuel, timeout, output-size, and concurrency limits.
  • Database, HTTP, file, clock, and secret access are host functions and must be explicitly granted by YAML.
  • JavaScript may remain an authoring language or a narrow development adapter, but it is never the server isolation boundary.

Source declaration in YAML

Inline source is convenient for authoring, but it is still compiled to WASM before deployment. The YAML definition records the source, compiler target, capabilities, and runtime limits.

# datasource with inline JavaScript
datasources:
  - id: enriched-orders
    language: javascript
    roles: [admin, sales]
    permission: "orders.read"
    script: |
      const orders = await ctx.datasource("recent-orders");
      const enriched = orders.map(order => ({
        ...order,
        tax: order.total * 0.08,
        grand_total: order.total * 1.08,
        priority: order.total > 10000 ? "high" : "normal"
      }));
      return enriched;
    component: data-table

  # datasource with inline Python
  - id: sales-forecast
    language: python
    roles: [admin, analyst]
    permission: "reports.forecast"
    script: |
      import pandas as pd
      orders = ctx.datasource("recent-orders")
      df = pd.DataFrame(orders)
      df['date'] = pd.to_datetime(df['created_at'])
      monthly = df.groupby(df['date'].dt.to_period('M'))['total'].sum()
      forecast = monthly.rolling(3).mean().iloc[-1]
      return { "monthly": monthly.to_dict(), "next_month": forecast }
    component: summary-card

External source file

For larger scripts, reference an external source file. The build pipeline resolves the path relative to the YAML file, compiles the source to WASM, and deploys the compiled artifact with its checksum and capability manifest:

datasources:
  - id: inventory-sync
    language: python
    roles: [admin, warehouse]
    permission: "inventory.sync"
    script_file: ./scripts/inventory_sync.py
    params:
      warehouse_id: { type: string, from: route }
    timeout: 30s

  - id: custom-validation
    language: typescript
    roles: [admin]
    permission: "po.validate"
    script_file: ./scripts/validate_po.ts
    params:
      po_id: { type: uuid, bind: po-detail.id }

Execution context

Every WASM module receives a typed host context with only the capabilities granted by YAML. The module cannot access the server runtime directly:

interface ScriptContext {
  user: User;                                       // current authenticated user
  params: Record<string, any>;                      // resolved YAML params
  datasource(id: string): Promise<any>;             // fetch another datasource
  db: IRepository;                                  // direct DB access (permission-gated)
  http: { get, post, put, delete };                 // sandboxed HTTP client
  log: Logger;                                      // structured logging
  env: Record<string, string>;                      // allowed environment variables
}
